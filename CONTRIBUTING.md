# Руководство для участников

Спасибо, что хотите улучшить руководство по стилю. Этот файл описывает, как предложить изменение.

## Как предложить изменение

1. Создайте Issue с описанием проблемы или идеи либо сразу переходите к правкам, если изменение небольшое.
2. Сделайте форк репозитория или создайте ветку, если у вас есть права на запись.
3. Внесите изменения и проверьте их локально (см. ниже).
4. Откройте Pull Request в ветку `main`.

В описании Pull Request укажите, что изменено и зачем, а при необходимости — ссылку на Issue.

## Названия веток

Формат: `тип/краткое-описание`, например `docs/accessibility-rules` или `fix/typo-in-glossary`.

## Требования к коммитам (Conventional Commits)

Формат сообщения:

```text
<тип>(<область>): <краткое описание>

<необязательное подробное описание>
```

Типы:

| Тип | Когда используется |
|---|---|
| `docs` | Изменение текста руководства |
| `feat` | Новый раздел или новая возможность сайта |
| `fix` | Исправление ошибки, опечатки, битой ссылки |
| `style` | Правка оформления без изменения смысла |
| `refactor` | Перестройка структуры без изменения содержания |
| `ci` | Изменения в конфигурации CI/CD |
| `chore` | Прочие служебные изменения |

Правила:

- описание пишется в повелительном наклонении, со строчной буквы, без точки в конце;
- первая строка — не длиннее 72 символов;
- один коммит — одно логическое изменение.

Примеры:

```text
docs(accessibility): add rules for alt text
fix(glossary): correct definition of pull request
ci: add markdownlint to workflow
```

## Процесс ревью

1. Автор открывает Pull Request. CI запускает линтер и сборку.
2. Если проверки не прошли, автор исправляет ошибки.
3. Рецензент оставляет комментарии: замечания, предложения и вопросы. Минимум один рецензент должен одобрить изменения.
4. Автор вносит правки новым коммитом в ту же ветку и отвечает на комментарии.
5. После одобрения и успешных проверок изменения вливаются в `main`.
6. После слияния сайт автоматически публикуется на GitHub Pages. Проверьте, что изменения появились на сайте.

Что проверяет рецензент:

- соответствие правилам руководства;
- точность и понятность текста;
- работающие ссылки и корректную навигацию;
- отсутствие ошибок линтера.

Комментарии пишите доброжелательно и по существу, предлагайте конкретную формулировку.

## Как запустить локальную сборку

1. Установите Python 3.10 или новее.
2. Установите зависимости:

   ```bash
   pip install -r requirements.txt
   ```

3. Запустите сервер с автоматической перезагрузкой:

   ```bash
   mkdocs serve
   ```

4. Откройте `http://127.0.0.1:8000` в браузере.
5. Перед отправкой проверьте строгую сборку и линтер:

   ```bash
   mkdocs build --strict
   npx markdownlint-cli2 "docs/**/*.md" "README.md" "CONTRIBUTING.md"
   ```

## Как добавить новый раздел

1. Создайте файл в каталоге `docs/`. Имя — строчными латинскими буквами через дефис, например `docs/code-examples.md`.
2. Начните файл с заголовка первого уровня.
3. Добавьте раздел в навигацию в `mkdocs.yml`:

   ```yaml
   nav:
     - Примеры кода: code-examples.md
   ```

4. Запустите `mkdocs serve` и проверьте, что раздел появился в меню.
5. Зафиксируйте изменения коммитом, например `feat(docs): add code examples section`.
6. Откройте Pull Request.
