# Точечные рекомендации

Короткие правила для ситуаций, которые часто встречаются в документации и не вошли в общие разделы.

## Путь в интерфейсе

Пишите путь полужирным через стрелку: «Откройте **Настройки → Учётная запись → Безопасность**». Название каждого элемента — как в интерфейсе, с сохранением регистра.

## Сочетания клавиш

Клавиши пишите в `<kbd>`: <kbd>Ctrl</kbd> + <kbd>S</kbd>. Если сочетания различаются для систем, укажите оба: «<kbd>Ctrl</kbd> + <kbd>S</kbd> (Windows и Linux), <kbd>Cmd</kbd> + <kbd>S</kbd> (macOS)».

## Заменяемые значения

Заменяемые значения в примерах пишите заглавными буквами через дефис и поясняйте под примером:

```bash
git clone https://github.com/YOUR-USERNAME/style-guide-project.git
```

Замените `YOUR-USERNAME` на ваш логин GitHub.

## Примеры данных

- Для доменов используйте `example.com`.
- Для адресов электронной почты — `user@example.com`.
- Не используйте в примерах реальные пароли, токены и персональные данные.

## Предупреждения

- Предупреждение ставьте перед шагом, к которому оно относится, а не после.
- Для риска потери данных используйте блок `warning`, для полезных замечаний — `note` или `tip`.
- В одном разделе — не более двух блоков примечаний.

## Номера версий и даты

Указывайте версию, к которой относится описание: «Начиная с версии 2.1». Не пишите «новая версия» и «недавно»: эти слова быстро устаревают.

## Сообщения об ошибках

Сообщение приводите точно, как оно выводится в продукте, в блоке кода. Рядом укажите причину и решение.

## Вопросы и ответы

Не создавайте разделы FAQ как свалку вопросов. Если вопрос повторяется, включите ответ в соответствующий раздел руководства.
